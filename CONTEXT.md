# CONTEXT.md — Help Desk AI Agent

Глоссарий домена. Правила из `steps/` (Hexlet 425) + соглашения, принятые в ходе рефакторинга варианта A.

## Термины

### Тикет (ticket)
Обращение пользователя в службу поддержки, создаваемое **агентом** через MCP-инструмент `create-ticket`. Хранится в таблице `tickets`. Поля: `id`, `user_id` (email отправителя), `category` (`bug|docs|feature|access`), `status` (`open|answered|escalated|closed`), `text` (текст обращения **после PII-маскирования**), `created_at`, `updated_at`.
- **Авторитет создания — только агент.** Poller/sender не создают и не «исправляют» тикеты. Никакого «корректирующего слоя» (перезаписей текста тикета) нет.
- Текст тикета агент берёт из `text = user_id + текст письма`, который передаёт ему poller. Агент сам извлекает исходный вопрос из всего тела письма (включая цитаты треда) и передаёт его в `create-ticket`.
- Первая запись в `messages` (role=`user`) пишется автоматически внутри `create-ticket`.

### Сообщение / реплика (message)
Строка истории диалога в таблице `messages`. Поля: `id`, `ticket_id`, `role` (`user|agent`), `text` (после PII-маскирования), `model`, `tokens_in`, `tokens_out`, `latency_ms`, `created_at`.
- `messages` нужна **для разбора и учёта токенов, а не для памяти агента**. Обратно её не читает никто — историю в почте приносит сам клиент, цитируя переписку.
- **Источники записи в `messages`:** первая role=user строка — внутри MCP `create-ticket` (вызов агента); role=agent строка с токенами — прямой HTTP-вызов poller'а (`YdbMessageSaver.trySave` → `append-message`). Poller в БД **кроме role=agent-строки не пишет**.
- Для `role=agent` poller обязан передать `model`, `tokens_in`, `tokens_out`, `latency_ms` из `usage` Responses API (требование шага 9, сверка ≤10%). Агент своих счётчиков не видит — токены знает только poller.
- Рекомендуемая структура тикета: ровно 2 строки — role=user (из `create-ticket`) и role=agent (из `append-message` после `create-ticket`). Без дублей.

### Путь записи (persistence path)
Механизм, который кладёт данные в YDB.
- **`create-ticket` — только агент** через MCP-шлюз `ydb-tickets` (создаёт тикет + первую строку `messages` role=user, текст = дословные слова клиента). Poller тикеты не создаёт и не «исправляет».
- **`role=agent` строка с токенами — пишет poller** напрямую по HTTP к `ydb-tickets` через `append-message` (`YdbMessageSaver.trySave`), передавая реальные `model`/`tokens_in`/`tokens_out`/`latency_ms` из usage Responses API (шаг 9: «доставайте их отдельно» — poller авторитетный источник usage, LLM своих счётчиков не видит).
- **Агент `append-message` не вызывает** — иначе дубль agent-строки.
- **Не используем:** `update-ticket-text` / `update-ticket` — этого action нет и быть не должно (вне ТЗ, удалено рефакторингом). Корректность `text` в `create-ticket` — зона ответственности агента через инструкцию («дословно, без пересказа»).

### Транспорт-сообщение пользователя
Poller передаёт агенту в `input` **полное тело входящего письма** (`text`) — со всеми цитатами треда, без разбора и без отдельных полей, **после PII-маскирования** (маскируется на входе poller'а, до промпта агента).
- Не используем `original_text`, `thread_text`, и никаких парсеров `>`-цитат.
- Разбор «чей это текст / где исходный вопрос» — ответственность агента (LLM), не poller'а.

### Отправка письма пользователю (threading)
Poller отвечает тому же отправителю по SMTP с темой `Re: <subject>`, заголовками `In-Reply-To`/`References` (для группировки тредов в почтовом клиенте) и цитированием исходного письма в теле ответа. Цитирование — пользовательские данные в почте, PII там не маскируется (маскирование — на входе poller'а и на границе записи в YDB). При блокировке инъекции текст атаки не цитируется (`sendWithThreading(..., null)`).

## Отношения
- `ticket` →* `message` (один тикет, много реплик; PK `(ticket_id, id)`).
- `user_id` в `tickets`/`messages` — email отправителя (технический идентификатор канала, **не маскируется**).
- `create-ticket` создаёт тикет **и** первую role=user строку за одну операцию.

## Trusted / Untrusted
- **Trusted:** системный промпт агента, конфиг MCP-tools, код Cloud Functions.
- **Untrusted:** текст пользователя (тело письма, цитаты), RAG-документы.
- Правило: untrusted передаётся только как `input` агенту, никогда не интерполируется в trusted-контекст (системный промпт). PII маскируется **на входе в email-poller** (`PiiMasker` — до промпта агента и до классификатора) и **повторно на границе записи в YDB** (`ydb-tickets` -> `PiiMasker`). В почтовом ответе (цитата исходного письма) текст не маскируется — это канал пользователя.
- **Prompt injection проверяется на входе в email-poller** (`InjectionClassifier`, первая линия): `injection` → нейтральный ответ «У меня нет информации по этому вопросу в базе знаний…», агент не вызывается, тикет не создаётся, в лог пишется `ALERT_INJECTION_BLOCKED` с замаскированным текстом. Вторая линия — `ydb-tickets` **на всей границе записи**: и `create-ticket`, и `append-message` (`{"error":"Запрос заблокирован модерацией"}` + `ALERT_INJECTION_BLOCKED`) — защита от обхода через прямой MCP-вызов (append-message отдан модели через `allowedToolsOfMcp`, поэтому проверяется так же, как create-ticket).
