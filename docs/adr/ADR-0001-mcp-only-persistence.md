# ADR 0001 — Единственный путь записи в YDB через MCP-агента

- Статус: принято (2026-09-07), пересмотрено (2026-09-07) — см. «Изменения»
- Контекст: `docs/adr/ADR-0001.md`

## Контекст

При развитии проекта «Help Desk AI Agent» (Hexlet 425, шаги 1–9) точку «тикет ↔ messages» несколько раз переделывал агент, навешивая слои страховок поверх исходного MCP-контракта. Последний коммит `fbb13f4` добавил:

- парсер `>`-цитат `extractDeepestQuoted` и поле `original_text`/`thread_text` в `input` агенту;
- новый `action=update-ticket-text` (4-й инструмент, вне ТЗ: `create-ticket`/`list-my-tickets`/`append-message`);
- прямое обращение poller'а к CF `ydb-tickets` по HTTP (`YdbMessageSaver.trySave`/`tryCorrectTicketText`) для дублирования записей в `messages`.

Всё это добавлялось как страховка от того, что LLM-агент не «правильно» создаст тикет и не передаст токены. Итог — дубли в `messages` (по 2 role=user и по 2 role=agent на тикет), split-brain между «агентом через MCP» и «poller'ом напрямую через HTTP», лишний action вне контракта ТЗ.

## Решение

Свести к **одному авторитетному пути записи** — агенту через MCP:

- `create-ticket` пишет тикет + первую строку `messages` (role=user).
- Агент вызывает `append-message` (role=user/agent) для остальных реплик, передавая `model`/`tokens_in`/`tokens_out`/`latency_ms` из `usage` (для role=agent).
- Poller (`email-poller`) — только транспорт: IMAP → LLM → SMTP, плюс журнал `EMAIL_TOKENS`/`TOKENS_USAGE`. Прямых HTTP-записей в YDB нет.
- Удаляем: парсер `>`-цитат и поля `original_text`/`thread_text` (агенту передаётся полное тело письма как `text`), `action=update-ticket-text`/`update-ticket`, класс `YdbMessageSaver`.

> Уточнено разделом «Изменения»: poller вернулся как единственный писатель role=agent с реальным usage; класс `YdbMessageSaver` восстановлен в урезанном виде (только `trySave`).

## Последствия

Плюсы:
- Один источник истины для `messages`, гарантированная структура «2 строки на тикет» при штатном сценарии.
- Соответствие ТЗ: ровно 3 MCP-инструмента, агент авторитетен для тикета.
- Меньше кода и меньше поверхность для инъекций (нет лишнего action).

Минусы и риски:
- **Дисциплина агента.** Единственный источник `messages` — вызовы `append-message` самим агентом. LLM-недетерминизм может пропустить вызов → в `messages` не будет agent-строки/токенов, и сверка шага 9 (≤10%) по этому диалогу не сойдётся. **Риск принят осознанно.** Компенсация — жёсткая инструкция агента и QA-чеклист, а не кодовая страховка.
- Агент должен сам извлекать исходный вопрос из тела письма с цитатами (без `original_text`-подсказки). Ожидаемо для LLM.
- любой будущий fallback-путь записи снова раздваивает источник истины — должен проходить через это решение и CONTEXT.md.

## Изменения (2026-09-07, после продакшен-проверки)

Продакшен-проверка показала: риск «дисциплины агента» реализовался. LLM-агент **физически не видит** свои `tokens_in`/`tokens_out`/`latency_ms` — это метаданные вызова Responses API, не приходящие в контекст модели. Инструкция «передай токены из usage» неисполнима буквально: в реальном прогоне агент не вызвал `append-message` с role=agent, и в `messages` осталась только строка role=user с нулевыми токенами (сверка шага 9 невозможна).

Также выяснилось, что исходная трактовка ТЗ (комментарий в `EmailHandler` до рефакторинга) предусматривала ровно это: **«доставайте их отдельно» — poller является авторитетным источником usage**. Требование шага 9 — чтобы в `messages` лежали *фактические* токены; их знает только poller.

### Скорректированное решение

- **`create-ticket`** — по-прежнему вызывает только агент через MCP; создаёт тикет + первую строку `messages` (role=user, текст = дословные слова клиента). Авторитет создания тикета — только агент.
- **`append-message` (role=agent) — дописывает poller** напрямую по HTTP к `ydb-tickets` (`YdbMessageSaver.trySave`), передавая реальные `model`/`tokens_in`/`tokens_out`/`latency_ms` из своего `AgentResult` (usage Responses API). Это гарантирует наличие agent-строки с фактическими токенами в каждом тикете (структура «2 строки на тикет»).
- **Агент не вызывает `append-message` вообще** — иначе появится дубль agent-строки. Инструкция обновлена.
- **`update-ticket-text` по-прежнему удалён** — корректность `text` в `create-ticket` обеспечивается строгой инструкцией агенту («дословные слова клиента, без пересказа»), а не коррекционным слоем.

Что из исходного решения сохранилось: удаление `extractDeepestQuoted`/`original_text`/`thread_text`, удаление `update-ticket-text`/`update-ticket`, ровно 3 MCP-инструмента, отсутствие дублей в `messages`.
